## 总体结论

前端可以围绕“批次工作台”重构，但必须区分两件事：

1. 当前后端已经支持的主流程是：上传 Excel → 生成工作包 → 生成供应商推荐 → 导出结果。
2. 当前后端尚未实现安全、完整的人工调包与最终供应商确认。若新界面要把“人工调整零件所在包”作为核心能力，后端必须先补专用接口、业务校验、统计同步及推荐失效机制，不能直接调用通用零件修改接口实现拖拽。

## 1. “Excel ID”是否就是 `batchId`？不同上传批次是否完全隔离？

**结论：在当前模型中，可以把所谓“Excel ID”理解为 `batchId`；每次上传都会创建一个新批次。批次隔离是正确的目标模型，但现有后端并没有完整强制这种隔离。**

代码事实：

- `BatchImportServiceImpl.importExcel()` 每上传一次 Excel，就新建一条 `SUBCONTRACT_BATCH`，并返回 `batchId`、`batchNo`。
- 本次成功导入的全部 `BATCH_PART` 都回填该次生成的 `batchId`。
- 分包时，`WORK_PACKAGE.batchId` 也使用这个批次 ID。
- 后端不存在名为 `excelId` 的独立业务字段。界面和接口应统一使用 `batchId`；`batchNo` 用于展示，不应替代主键。

但需要特别注意：

- 当前 DDL 没有外键约束。
- 通用 `PUT /api/part/batch-part` 只校验零件记录是否存在，不校验目标 `packageId` 是否与零件属于同一个 `batchId`。
- 因此，“不能跨批次移动”目前是应当遵守的业务约束，并非后端已经可靠执行的约束。

前端重构应按“一个工作台只操作一个 `batchId`”设计；后端人工移包接口必须强制验证源包、目标包、零件三者属于同一批次。

## 2. 上传后自动分包，还是再点击“生成工作包”？

**结论：当前后端是明确的两步流程，上传不会自动分包。建议界面保留“生成工作包”这个业务动作。**

当前状态变化为：

1. `POST /api/subcontract/batch/upload`：解析 Excel、创建批次和零件，批次状态变为 `DATA_READY`。
2. `POST /api/subcontract/batch/{id}/package`：执行分包，状态变为 `PACKAGED`。

另有 `POST /api/subcontract/batch/{id}/run`，它会一次执行“分包 → 推荐 → 回写推荐结果”，但上传接口本身没有调用它。

因此界面建议采用：上传 Excel → 解析结果/错误确认 → 进入批次工作台 → 点击“生成工作包”。不建议把当前实现描述成“上传成功即自动生成工作包”。

## 3. 人工把零件从包 A 移到包 B，是否应成为核心操作？

**结论：从重构目标看，适合把它作为批次工作台中的核心人工操作；但当前后端尚未提供可用的人工调包能力。**

界面形态可以采用同页的“左侧工作包 + 右侧零件列表/抽屉”，支持选择后移动；拖拽可以作为效率增强，但必须同时提供键盘可操作的“移动到”动作。

当前后端只有通用零件修改接口。直接修改 `BATCH_PART.packageId` 会产生以下问题：

- 不同步 `PACKAGE_PART` 关联表；
- 不同步源包和目标包的 `partCount`；
- 不重新计算包的品类、零件类型、容量等派生数据；
- 不改变批次或工作包推荐状态；
- 不删除或作废旧推荐；
- 不校验跨批次移动。

所以，前端不能把通用 `PUT /api/part/batch-part` 当作正式拖拽接口。后端应增加事务性的专用“移动零件/移动原子组”接口后再开放此交互。

## 4. 零件移动有哪些硬性限制？管理员能否强制移动？

**结论：自动分包代码表达了若干规则，但当前人工修改路径一条也没有强制校验。建议第一版专用移包接口严格执行规则，不默认提供绕过规则的管理员强制移动。**

自动分包的现有规则为：

- **三级品类：必须相同。** 自动分包第一层按“三级品类 + 供应商需求数”分组。
- **供应商需求数：必须相同。** 这也是工作包的基础分组条件，原问题中未单列，但移动时必须校验。
- **零件类型：代码没有要求必须完全相同。** 当前算法取包内出现最多的类型作为 `partType`，再据此取容量。因此不能宣称现有业务规则是“同包必须同零件类型”。如果业务希望严格同类型，需要修改分包和移包两处规则。
- **包容量：自动分包会应用容量上限。** 小型/中型/大型/超大型/其他有默认值，也可由数据库配置覆盖。人工移动接口当前没有容量校验。
- **相同 `nestingInfo`：代码意图是必须同包。**
- **左右件：代码意图是必须同包。** 左右件来自机型+图号后缀规则或人工维护的左右件主数据。

还发现一个实现风险：`mergeNestingAndLeftRight()` 只是把关联零件排到一起，随后又按单个零件数量切包，因此原子组正好跨越容量边界时仍可能被拆开。也就是说，“套裁/左右件强制同包”是代码注释和业务意图，但当前算法实现未完全保证，需要后端修复。

建议专用移包接口执行：

1. 只允许同 `batchId`；
2. 校验三级品类和供应商需求数；
3. 校验目标包容量；
4. 将相同 `nestingInfo` 和左右件作为不可拆分原子组一起移动；
5. 原子更新两张关联数据、两个包的统计和推荐状态。

如果确实需要管理员越权，应另设“带原因的强制移动”接口并记录审计日志，而不是让普通更新接口静默绕过规则。这属于尚需业务确认的新能力。

## 5. 移动零件后，供应商推荐是否必须重新计算？

**结论：必须。源包和目标包的旧推荐都应立即失效，然后重新推荐。当前通用更新接口不会自动完成这件事。**

推荐记录绑定 `packageId`，历史供应商又从该包当前关联的零件中读取。移走或移入零件都会改变推荐输入，因此原推荐已不再可信。

建议后端在一次移包事务中：

- 删除或标记源包、目标包的旧推荐结果失效；
- 清空相关零件上已回写的 `recommendSupplier1...7`；
- 将两个包的 `recommendationStatus` 置为 `PENDING`；
- 将批次状态从 `RECOMMENDED/COMPLETED` 回退到 `PACKAGED`；
- 由用户点击“重新推荐”，或在移动确认后明确选择自动重算。

当前 `recommendForPackage()` 在重新推荐单个包时会先删除该包旧推荐，这是可复用的行为；但通用零件修改不会触发它。

## 6. “对应供应商信息”是推荐供应商，还是最终确定供应商？

**结论：当前后端只有推荐供应商，没有“最终确定/承制供应商”业务模型。**

现有 `PACKAGE_SUPPLIER_RECOMMENDATION` 只保存：

- 推荐顺序；
- 供应商；
- 推荐来源；
- 质量等级；
- 绩效分数。

没有选择状态、最终供应商、确认人、确认时间或确认动作。导出时只是把推荐名称按顺序回写到 Excel 的推荐供应商 1—7，并把批次置为 `COMPLETED`。

因此当前系统语义是“生成推荐清单并导出到后续环节”，不是“系统内从 6 家中最终选择 2 家”。如果业务确实要求最终定商，需要新增数据表/字段、确认接口、状态流转、审计和导出规则；前端不能仅凭现有 API 画出可落地的“确认供应商”功能。

## 7. “供应商需求数 + 4”是否为固定规则？

**结论：是。当前代码中它是固定规则，不可由用户配置。**

工作包生成时直接执行：`recommendCount = supplierCountNeeded + 4`；推荐时若 `recommendCount` 为空，也使用相同公式兜底。数据库仅保存计算结果，没有 `+4` 的系统配置项。

所以当前界面只需展示“需 N 家，系统推荐 N+4 家”，不需要提供配置入口。如果以后业务要调整，应由后端把冗余数参数化，而不是前端自行计算不同规则。

## 8. 推荐是否严格按 HISTORY → QUALITY_ROUND → NORMAL_ROUND → ALL_CATEGORY 四层阶梯？

**结论：不是这个四层顺序。`ALL_CATEGORY` 是特殊品类的前置分支，不是普通推荐不足时的最后兜底。**

当前实际逻辑：

- 特殊品类且规则为 `ALL_SUPPLIERS`：直接从该品类关联的全部启用供应商中取推荐，来源为 `ALL_CATEGORY`。
- 特殊品类且 `ignoreQuality=1`：直接执行不区分优质/普通的轮询，来源在代码中为 `ROUND_ROBIN`。
- 其他普通情况：先取历史供应商 `HISTORY`；不足部分先补优质 `QUALITY_ROUND`，再补普通 `NORMAL_ROUND`。

普通品类在历史、优质、普通仍不足时，代码不会再回退到 `ALL_CATEGORY`。因此前端可以解释推荐来源，但不要把四种来源画成对所有包都适用的固定四级漏斗。

另有契约差异：实体注释只列 `HISTORY / QUALITY_ROUND / NORMAL_ROUND / ALL_CATEGORY`，但忽略质量的特殊分支实际写入的是 `ROUND_ROBIN`。前端枚举和后端契约应先统一。

## 9. 轮询游标如何消费？

**结论：常规优质/普通轮询是“每成功选中一家就更新游标”，但代码不是简单连续消费；题目给出的两个例子都不完全符合当前实现。**

常规分区轮询中，每个“品类 + 年月 + 质量等级”各有一个游标：

- 每个包最多先取 2 个优质供应商；
- 优质第一次偏移 `+1`，成功后更新游标；第二次再基于新游标偏移 `+2`；
- 随后普通供应商依次按 `+1、+2、+3……`，每成功一次又更新游标。

若优质池为 A、B、C、D、E，初始游标为 0：

- 包 1 的优质部分会取 A、C，而不是 A、B、C；若还需要第 3 家，则转入普通池。
- 此时优质游标为 3；包 2 的优质部分会从 D 开始，第二家按当前算法会绕回 A。

因此它既不是“包 1 取 A/B/C，包 2 从 D 开始”的连续块模型，也不是“每个包只前进一位”的滑窗模型。

只有 `ignoreQuality=1` 的纯轮询特殊分支更接近连续块：例如一次取 A/B/C 后游标整体推进 3，下一包从 D/E/A 开始。

当前常规偏移算法很不直观，可能导致 B、E 等供应商的实际覆盖不符合业务预期。建议产品方确认真正想要的是“连续消费”还是“滑窗”，随后让后端调整算法；UI 不应尝试复刻或预测当前游标细节。

## 10. “上传排名进行打分”实际是哪一种？

**结论：当前正式上传流程是 A：上传每月绩效分数，系统自动计算综合得分并生成品类排名。**

正式上传模板只有两列：

- 供应商名字；
- 绩效成绩。

年份、月份由请求参数传入。系统计算半年平均和综合得分，再按供应商关联的各三级品类分别生成排名，前 30% 标为“优质”，其余为“普通”。没有正式的人工评分维度，也没有人工直接调整最终排名的业务动作。

虽然通用 CRUD 接口技术上允许直接保存/修改绩效和排名快照，但它们没有形成“人工打分/人工改排名”的业务规则，不应据此把界面设计成 B、C 或 D。

此外源码存在一个应由后端确认的公式差异：实现使用“半年平均 × 60% + 本次上传成绩 × 40%”，而 DDL 注释写成“半年平均 × 60% + 上月成绩 × 40%”。界面暂时不要写死公式说明，直到后端/业务统一口径。

## 11. 供应商“品类关联”是否就是推荐资格池？

**结论：基本正确，它是多对多的品类资格池；但历史供应商是当前代码中的例外。**

`SUPPLIER_CATEGORY` 保存 `supplierId + categoryId`。排名生成只会对已关联该品类且启用的供应商排名；特殊品类“全部供应商”也只取该品类关联的启用供应商。因此常规轮询候选池来自该关联关系。

但历史供应商逻辑直接读取包内零件的历史供应商名称，只校验供应商存在且启用，没有校验其是否关联当前三级品类。也就是说，历史供应商可能绕过品类资格池。

如果业务规则是“任何来源都必须具备当前品类资格”，后端需要给历史供应商分支补品类关联校验；在修复前，前端不能宣称这是无例外的硬规则。

## 12. 是否把供应商管理、绩效、排名、品类关联聚成“供应商中心”？

**结论：认同。界面信息架构应以供应商实体为中心聚合，但无需强行把后端四组资源合成一个接口。**

推荐结构：

- 供应商列表作为一级入口；
- 供应商详情内提供“基础信息 / 承制品类 / 月度绩效 / 综合得分与品类排名 / 推荐历史”；
- 月度绩效批量上传保留为供应商中心的全局动作；
- 排名快照主要作为查询和故障排查视图，不作为普通用户一级业务入口。

后端资源虽然分表、分 Controller，但都围绕同一个 `supplierId`，前端聚合不会破坏接口边界。需要补充的是“推荐历史”聚合查询接口；现有推荐分页可以按供应商过滤的能力还需在联调时确认。

## 13. 排名快照生成是否需要普通业务用户感知？

**结论：正常流程不需要。当前绩效上传成功后已经自动生成当月排名快照。**

`POST /api/supplier/performance/upload` 在至少一行上传成功后会调用 `generateRanking(year, month)`。自动生成失败不会回滚已上传绩效，只记录日志；后端保留手动 `ranking-snapshot/generate` 用于重试。

因此界面建议：

- 普通流程显示“绩效导入成功，排名已更新”；
- 若自动生成失败，显示明确的“排名生成失败，可重试”状态；
- 手动生成入口仅作为管理员/运维修复动作，不做成普通用户每月必点的流程步骤。

当前代码没有“上传后待审核再生效”的状态，所以不能按人工审核流程设计，除非业务明确新增审核机制。

## 14. 特殊品类、左右件规则、手动左右件、容量配置是否都属于管理员配置？

**结论：从代码职责看，它们都是低频规则/主数据，适合统一收进“规则配置”，并仅向有配置权限的管理员开放。**

建议归入：

- 三级品类主数据；
- 特殊品类推荐规则；
- 左右件自动识别规则；
- 左右件人工维护；
- 工作包容量配置。

其中“左右件人工维护”是对无法自动识别的左右件关系进行主数据登记，不是批次工作台里的“手工移动左右件”。容量配置有代码默认值，并允许数据库配置覆盖，属于系统规则而非每批次参数。

当前源码只有接口权限码，无法仅凭代码确定实际组织角色分配。因此“普通分包人员不可见、管理员可见”仍需在 RBAC 中落实，但信息架构上不建议拆成五个一级菜单。

## 15. 日常 80% 核心链路是否应围绕“批次工作台”？

**结论：后端模型明显以批次为流程主轴，前端应围绕“批次工作台”设计；但当前可落地链路与提问中的目标链路有两处差异。**

当前后端已实现的链路是：

> 上传 Excel → 查看解析结果 → 生成工作包 → 生成供应商推荐 → 导出 Excel

当前未实现：

- 安全的人工调整零件所在包；
- 最终供应商确认。

因此推荐把未来目标工作台设计为：

> 上传 Excel → 解析校验 → 生成工作包 → 人工调整（后端补齐后开放）→ 推荐/重新推荐 → 复核推荐结果 → 导出 Excel

“复核推荐结果”可以是导出前检查，不应在没有后端模型时命名为“确认最终供应商”。

页面重构无需再按数据库资源拆成 18 个平级页面。批次详情可聚合状态、工作包、包内零件和推荐结果；供应商中心与规则配置作为低频支撑模块独立存在。这更符合当前后端以 `batchId` 驱动 `/package`、`/recommend`、`/run`、`/export` 的真实流程。

## 前端重构前必须要求后端补齐的事项

1. 新增专用人工移包接口，禁止以前端直接修改 `BATCH_PART.packageId` 代替。
2. 强制同批次校验，并事务性同步 `BATCH_PART`、`PACKAGE_PART`、两个工作包统计。
3. 明确并实现三级品类、供应商需求数、容量、套裁、左右件等移动约束。
4. 修复套裁/左右件原子组可能被容量切分的问题。
5. 移包后自动使源包、目标包推荐失效，并回退批次状态、清理 Excel 回写列。
6. 确认历史供应商是否必须通过品类资格校验。
7. 确认轮询真正需要“连续消费”还是当前累加偏移算法，并统一 `ROUND_ROBIN` 来源枚举。
8. 统一综合得分公式的代码与文档口径。
9. 明确系统是否只输出推荐清单；若需要最终定商，新增完整领域模型和流程。

## 主要源码依据

- `BatchController.java`：上传、分包、推荐、一键编排、导出接口。
- `BatchImportServiceImpl.java`：每次上传创建批次、回填 `batchId`、状态置为 `DATA_READY`。
- `SubcontractServiceImpl.java`：分包分组、套裁/左右件、容量及 `supplierCountNeeded + 4`。
- `BatchPartServiceImpl.java`：通用零件更新只校验记录存在。
- `RecommendationServiceImpl.java`：历史、特殊品类、优质/普通轮询、游标消费和旧推荐清理。
- `PerformanceController.java`、`PerformanceServiceImpl.java`：两列绩效上传、综合得分计算、自动生成排名。
- `RankingSnapshotServiceImpl.java`：按品类排名、前 30% 优质、上传后重置游标。
- `CategoryEntity.java`：供应商与三级品类多对多关联。
- `SupplierRecommendationEntity.java`：只有推荐结果，无最终定商字段。
- `BatchExportServiceImpl.java`：推荐回写 Excel，导出后批次置为 `COMPLETED`。
- `schema-dm.sql`：批次、零件、工作包、推荐、绩效、排名、游标及规则配置表结构。
